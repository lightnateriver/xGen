# H3 Native-stream VAE Decode 组件性能与精度

实验时新后端参数值为 `omni`，现已更名为 `native-stream`；只更名接口，不改变以下计算路径或历史测量结果。

Lightning 流式实验已回退；新增独立的原生 H3 VAE Decode 后端。当前 CUDA 推荐配方默认选择 native-stream；本页记录的是此前原生 FP32 存储的隔离组件测试，不是新默认组合的整网性能。

**范围：8×RTX 5090、1344×768、同 latent、原生 FP32 decoder/FP16 autocast、24 fps、x264 fast/CRF10、同 PCM。每形状预热一次、正式一次，取八 rank 最大时间。**
计时包含 latent H2D、VAE、RGB8/D2H、编码、音频封装及写文件；不含模型加载、Audio VAE、DiT 与验收。以下不是整网加速比。
xGen/Lightning 使用 Torch 2.12.0+cu130；原生 Omni 使用其原环境 Torch 2.14.0+cu130。两环境差异保留，不将小幅差异直接归因于框架。

## 精度

性能矩阵复用保存的首步 latent，只用于组件性能和技术验证。精度另使用两条既有 20-step 清晰成片，经 VAE encoder 的 posterior mode 生成公共 latent；不是原 DiT 最终 latent。比较完整分辨率、所有帧、H.264 编码前统一 round 的 RGB8。
Lightning 实际文件写入使用 truncation，新后端/native 使用 round；统一 round 数据用于隔离 decoder 差异，实际 MP4 不承诺哈希一致。

## 验证边界

- 18 项正式组件输出和 6 项清晰素材解码分别核对分辨率、帧数、音视频流、完整解码与 SHA-256。
- 101 项功能与回归测试通过，远端源码包缺少 Git 历史导致 5 项 AST 检查跳过；这 5 项已在本地真实 Git 历史下另外通过。13 个迁移方法 AST 也通过核对。
- 新后端功能测试：默认隔离、参数冲突、队列所有权、失败清理；八卡连续两次解码后 CPU master 稳定，一次预期发布失败在全 rank 传播并恢复。
- Lightning 与 Omni 的 tile 几何不同，两者都不是全画面全局 attention；需结合抽帧检查局部接缝及主体。
- 本报告不代表用户已经人工验收，也不证明所有输入、长时连续请求、DiT 常驻整网容量或 NPU 新后端可用。
- 成片使用同一冻结 PCM；本轮没有测 Audio VAE 或评价其生成质量。
- 模型初始化单列，VAE 组件常驻测试不含每请求权重 H2D；独立 API 暂存冒烟另检验 CPU master 恢复。

组件驻留峰值不能代表含 DiT 的整网峰值。5s 精度样例用于本次 decoder 比较；10s/15s 仅完成组件性能及技术验证，未据此宣称长视频生成精度通过。
