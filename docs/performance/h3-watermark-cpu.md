# H3 水印 CPU 增量基准

日期：2026-11-10。本地 Intel Core i7-1260P、Windows、16 逻辑核；1344×768 RGB8、24fps。没有加载模型、导入 Torch 或使用 GPU，不作为服务器推理 E2E 数据。

直接调用当前 xGen 的水印转换、RGB8 转换、FFmpeg 写入及原子发布函数。仅通过 AST 隔离模型导入，水印和编码真实执行。编码为软件 libx264、veryfast、CRF10、yuv420p、AAC，x264 默认线程数；配对只切换水印开关。

从已有成片取固定 24 帧缓冲循环输入（约 71 MiB），用于控制内存和比较同样的像素工作量，不用于画面语义/音画质量评估。5/10 秒沿用原生 padding 保存 124/243 帧，15 秒保存 360 帧。每项预热后编码配对 8 组、纯转换配对 10 组，结果为配对差值中位数。

| 请求时长 | 保存帧数 | 纯水印额外 CPU / s | 编码保存阶段净增 / s | 编码配对增量范围 / s |
|---|---:|---:|---:|---|
| 5s | 124 | 0.113 | +0.062 | +0.032 ～ +0.130 |
| 10s | 243 | 0.212 | +0.237 | +0.053 ～ +0.434 |
| 15s | 360 | 0.313 | +0.251 | +0.128 ～ +0.618 |

纯水印计时包含标识构造、每帧完整 RGB 复制和覆盖，不含 bytes/编码。编码保存包含帧转换、bytes/pipe、H264/AAC、封装、ffprobe 校验及原子发布，排除输入解码、音频 WAV 准备、模型、VAE、D2H 和网络交付。

CPU 帧处理与独立 FFmpeg 进程可以流水重叠，因此纯处理开销不能直接全部加到编码耗时。CPU 调度和编码复杂度也会造成净增波动；本机结果不能当作八卡服务器的实测增量。

48 条计时视频通过尺寸、帧数、24fps、视频包数和音轨检查；同条件重复输出 SHA-256 相同。三个时长的输出均解码检查水印区域，确认标识真正写入视频。本公开文档仅保留汇总数据和可复现脚本，不包含业务视频、提示词或机器地址。

## 复现

在仓库根目录执行，准备一份 1344×768、至少 24 帧且音轨不少于 15 秒的本地视频：

```bash
python tools/bench_h3_watermark.py \
  --input samples/video.mp4 \
  --output outputs/watermark-bench
```

依赖 NumPy、Pillow、ffmpeg 和 ffprobe，无需 Torch、CUDA 或模型权重。默认每项编码配对 3 组、纯转换配对 7 组；本表为首轮 3 组及确认轮 5 组编码数据合并，纯转换合计 10 组。可用 `--repeats` 和 `--overlay-repeats` 调整重复数。

输出包括 report.md、results.json、summary.csv、增量 progress.json 和各组视频；目标目录必须为空。实际视频时长为 5.167/10.125/15 秒，来自上述保存帧数。
